# ADR-0007: A serializable `RawFormPage` boundary; DOM selectors never become the data model

**Status:** Accepted
**Date:** 2026-08-04
**Phase:** P5

## Context

P5 (spec §10) asks CareerHQ to read a live employer career-site page — Greenhouse, Lever, or an unknown ATS — and turn whatever DOM it finds into a `CanonicalForm` the rest of the system can plan answers against, review, and submit. The only place that can see that DOM is a real, isolated Playwright browser context running in `apps/worker`; everything downstream (ATS detection, blocker detection, field mapping, answer planning, the review screen) is business logic that has no business touching a browser at all — spec §10.3 says as much directly: "DOM selectors are implementation details, never the data model."

The tempting shortcut is to let the parsing logic reach into the page directly — call `page.$$eval`, walk `ElementHandle`s, decide `canonicalField` while still inside `page.evaluate`. That collapses two very different concerns into one: "how do I get information out of this specific DOM" and "what does this information mean." It also makes every adapter (`parseGreenhouse`, `parseLever`, the generic fallback) and every regression fixture untestable without a real browser, which is slow, flaky in CI, and cannot be diffed as committed JSON.

## Decision

**The browser's only contract with the rest of the system is `RawFormPage`** (`packages/autoapply/src/raw.ts`) — a plain, JSON-serializable object: url, title, bodyText, rootMarkers, and a flat list of fields carrying selector, tag, type, name, id, labelText, nearbyText, placeholder, required, maxLength, accept, options, and step. `detectAts`, `detectBlockers`, `parseGenericForm`, and the Greenhouse/Lever adapters (`packages/autoapply`) are pure functions **over that struct** — no DOM, no `page`, no `document`, no imports from `apps/worker` or `playwright` anywhere in the package. `rawFieldId` derives each field's stable `CanonicalFormField.id` from a hash of its own `selector`, so the browser-facing identity and the canonical identity are two different, deliberately decoupled ids.

**Two implementations produce `RawFormPage`, kept honest by parity, not by promise.** The real one is `apps/worker/src/autoapply/extract.ts`'s `extractFromDocument`: written as a single self-contained function (every helper nested, no module-scope references) specifically so `EXTRACT_SCRIPT = \`(${extractFromDocument.toString()})(document)\`` can be handed to `page.evaluate` verbatim — the string the browser actually runs is derived from the function's own source, not a hand-copied twin of it. The test-only one is `packages/autoapply/src/testing/from-html.ts`'s `rawPageFromHtml`, which runs the identical labelText/nearbyText/selector/step rules against a `linkedom` document instead of a live page, exported only via the `@careerhq/autoapply/testing` subpath so the (`devDependency`-only) `linkedom` import never reaches a production bundle. `apps/worker/src/autoapply/driver.test.ts` asserts the two extractors agree field-for-field on the same fixture HTML — that assertion is what makes "these are the same rules" a checked fact rather than a comment.

**Fixture-testable adapters, with a hash tripwire against drift.** `packages/autoapply/fixtures/{greenhouse,lever}-page.json` are committed `RawFormPage` snapshots of `demo-ats`'s own markup, generated by `scripts/write-fixture.ts` and consumed directly by `greenhouse.test.ts`/`lever.test.ts` — no browser, no network, no `demo-ats` process, in CI or locally. `GREENHOUSE_FIXTURE_HASH`/`LEVER_FIXTURE_HASH` (`hashRawFormPage`, sha256 of the canonical JSON) are computed once from the committed fixture and compared in tests against a freshly-extracted hash of `demo-ats`'s live page: if the demo site's markup drifts without the fixture being regenerated, that comparison fails first, before any field-mapping assertion has a chance to fail confusingly downstream. `PARSER_VERSION` (`raw.ts`) is recorded on every `form_snapshots` row, so a schema or hint-table change is visible on old attempts without needing the hash tripwire to explain it retroactively.

**The same review/gate path serves any channel.** Because `CanonicalForm`/`PlannedAnswer` are channel-agnostic contracts, `apps/web/src/lib/site-submission.ts`'s orchestrator (prepare → refine → preview → confirm) is a straight structural cousin of the email channel's — same `evaluateSubmissionGates` matrix, same fingerprint-pinned preview/confirm/receipt shape, same `requiresUserBeforeSubmit` review gate — reusing P4's design (ADR-0002) rather than inventing a parallel one. Nothing about that path knows or cares that the payload came from a browser instead of an SMTP draft.

## Consequences

- **Positive:** adapters, blocker detection, and ATS detection are fixture-tested in milliseconds with zero browser and zero network — `greenhouse.test.ts`/`lever.test.ts`/`generic.test.ts`/`detect.test.ts`/`blockers.test.ts` all run against committed JSON or `rawPageFromHtml` output.
- **Positive:** parser drift is caught structurally, not by hoping someone notices a subtly wrong field mapping — a real markup change on `demo-ats` fails the hash tripwire before it can fail a mapping assertion in a way that looks like an adapter bug instead of a fixture-staleness bug.
- **Positive:** the review/gate/receipt machinery built for the email channel needed no redesign for company-site submission — only a new `SiteDeps.capture`/`submit` seam and a new payload shape, both of which slot into the existing three-layer gate (ADR-0002) unchanged.
- **Honest cost:** the in-page extractor and the linkedom test helper are genuinely two separate implementations of the same rules, not one shared module — `page.evaluate` cannot execute arbitrary imports, so the browser-side logic has to be self-contained. Parity is enforced by a test, not by the type system; a rule change made in one and not the other is a real, currently-undetected-until-CI-runs risk that this ADR accepts rather than eliminates.
- **Honest cost, by design:** the fingerprinted attachment filename (`attachmentFilename` in `site-submission.ts`, derived from the CV variant's label) intentionally differs from the on-disk basename — the payload the user confirms names the file the way a human reads it, not the way the file happens to be stored, and the fingerprint covers that human-readable name, not storage-layer detail that could change without the user's knowledge.
- **Risk to watch:** a real ATS tenant's markup outside `demo-ats`'s fixtures is untested by construction — the generic parser's lowered `parseConfidence` and the review screen's low-confidence flagging are the only safety net for a Greenhouse/Lever tenant whose conventions diverge from the committed fixtures, not a guarantee of correct mapping.

## Revision (2026-08-04)

Spec §10.6's original reading treated *any* required legal attestation as a permanent page-level blocker, checkbox or not — CareerHQ could parse `legal_attestation` but was never allowed to fill it, so a form carrying one could never reach "ready." In practice a required attestation **checkbox** is not CareerHQ answering on the user's behalf at all: it is field-level consent, structurally identical to a signature. The review screen renders it as an explicit, never-pre-ticked checkbox, with the exact attestation wording next to it; the user ticks it themselves, and only then does `legal_attestation` carry `source: "user"` into the fingerprinted payload and the confirmed receipt — the same box a human would tick if they filled the ATS form by hand.

A required attestation that is **not** a checkbox — a typed signature, a signature-date field, anything CareerHQ cannot render as a single honest tick — still cannot be completed on the user's behalf, and still pauses the attempt with a `legal_attestation` blocker exactly as before (proved end-to-end against `demo-ats`'s `/signature/jobs/:id` fixture in `apps/web/src/lib/site-e2e.test.ts`).

Consent given this way is never reused: `legal_attestation` and `criminal_history` are `CONSENT_ONLY_FIELDS` (`packages/core/src/autoapply/plan.ts`), refused a saved-answer shortcut even when a saved answer exists and even when an adapter fails to map the field at all (the label-regex half of `isConsentOnlyField` catches that case independently). Every application asks the question fresh, and every tick is the user's own.
