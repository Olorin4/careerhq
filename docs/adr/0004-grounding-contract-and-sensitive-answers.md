# ADR-0004: The grounding contract, and a conservative sensitive-answer policy

**Status:** Accepted
**Date:** 2026-08-03
**Phase:** P3

## Context

P3 (spec §7) asks the model to write cover letters, email bodies, and free-text application-question answers on the candidate's behalf. That is exactly the kind of task an LLM is worst at trusting blindly: a fluent, confident answer that invents an employer, a metric, or a start date is worse than no answer at all, because it reads as true. The product cannot simply ask the model to "only use real facts" and take its word for it — every free-tier model this project targets (ADR-0003) will occasionally comply imperfectly, and there is no way to distinguish a faithful answer from a fluent hallucination by reading the prose alone.

A second, distinct hazard sits next to the first: application questions routinely ask about work authorization, disability, race, salary history, notice period, and similar protected or high-stakes territory (spec §7.2.5). Some of these are illegal for an employer to ask in some jurisdictions; all of them are the kind of thing this project's cost/liability posture (a self-hosted, single-owner portfolio app) says should never be answered by an autonomous model on the user's behalf, confidently or otherwise.

Both hazards need a mechanism that does not depend on the model behaving well — the contract has to hold even when the model is wrong, evasive, or simply unavailable (no `OPENROUTER_API_KEY`, spec §1.4's deterministic floor).

## Decision

**Minimal fact subset in, structured citations out, deterministic post-validation that never trusts the model's own report of itself.** `selectFactsForGeneration` (`packages/core/src/grounding/select-facts.ts`) hard-excludes every fact with `sensitivity === "sensitive"` or `stale === true` before anything is scored — those facts are never in the candidate set, so they cannot be selected, cannot appear in the prompt, and cannot be cited, regardless of what the model does. The remainder is relevance-scored against the question/job context and capped at `MAX_GENERATION_FACTS` (12), so the model only ever sees a small, purpose-built subset, not the whole fact bank. `generateGrounded` (`packages/ai/src/tasks/generate.ts`) refuses to call the model at all when that subset is empty (`no_facts_provided`) — an empty-input guard, same lesson as `rerank`'s in ADR-0003. The model is asked to return `generationResultSchema` (`packages/contracts/src/index.ts`): an answer plus `factIds` it claims to have used, a `confidence`, and any `unsupportedClaims` it admits to. None of that self-report is trusted as the final word — `validateGeneration` (`packages/core/src/grounding/validate.ts`) independently checks the result against the fact ids that were actually provided (not the ones the model claims): any cited id outside the provided set, an empty `factIds`, a non-empty `unsupportedClaims`, confidence below `MIN_GENERATION_CONFIDENCE` (0.6), or a present `clarificationNeeded` all fail validation deterministically, in code, regardless of how confident the prose sounds.

**`NEEDS_FACTS` is a feature, not a failure.** Every path that can't ground an answer — an empty selected-fact subset, a `no_facts_provided` guard, or a `validateGeneration` failure — converges on the same `{ status: "needs_facts", reasons }` outcome (`runGeneration` in `apps/web/src/lib/generation.ts`), and `finalizeGeneration` never persists anything for it: no document row, no answer row, nothing half-written. The UI (`materials.tsx`'s `OutcomePane`) surfaces the reasons verbatim and links to "add a verified fact," treating the refusal as informative product behavior rather than an error to hide.

**Sensitive-question policy: a conservative keyword ruleset first, an LLM tie-break that can only widen, a hard block before generation, manual-only after.** `classifyQuestionSensitivity` (`packages/core/src/grounding/sensitive.ts`) matches a flattened keyword list drawn from spec §7.2.5's categories (work authorization, disability, demographics, criminal history, compensation, availability, relocation, attestations) — single words with word-boundary regex, multi-word phrases with substring match, chosen deliberately over stemming/NLP so the rule is auditable and has no false-negative surface from an unhandled inflection. `prepareGeneration` (`apps/web/src/lib/generation.ts`) runs this ruleset first, and only calls `classifySensitiveLlm` (`packages/ai/src/tasks/classify-sensitive.ts`) — a fast-tier tie-break — when the ruleset alone said "not sensitive," never the reverse. `mergeSensitivityRulings` (`packages/core/src/grounding/sensitive.ts`) enforces a **widen-only** merge: the ruleset can never be overruled by the model (`ruleset.sensitive` short-circuits to `true`), and the model's only lever is to flag a question the ruleset missed (`llmSaysSensitive === true` also yields `true`); a `false` or `null` from the model changes nothing. Either way, `sensitive_blocked` is returned before `generateGrounded` is ever invoked — the writing model never sees a sensitive question's text at all — and the only route to an answer is the manual form (`saveManualAnswerAction` in `qa-actions.ts`), which is also the only code path allowed to persist `sensitivity: "sensitive"` on an answer row.

**Record/replay for demo and CI determinism.** `withReplay` (`packages/ai/src/replay/index.ts`) wraps every AI call site behind `AI_MODE` (`live` | `record` | `replay`, `packages/config`): `record` runs live and persists `{value, model}` to a filesystem store keyed by a hash of the exact prompt (`replayKey`); `replay` never calls the model at all and returns the recorded fixture (or a structured `replay_miss`, never a thrown exception, on a missing/corrupt fixture). This lets CI and a scripted demo run the exact same grounding/validation/sensitivity code paths deterministically, with fixtures committed to the repo, with no live key and no network flakiness — while `live` mode (the default) is byte-identical to calling the real client directly.

## Consequences

- **Positive:** the grounding guarantee holds even against a model that lies about its own output — `validateGeneration` checks facts actually given, not facts claimed, so a compromised, confused, or adversarially-prompted model still cannot get an ungrounded claim persisted as an approved-looking draft.
- **Positive:** the sensitive-question block is provable independently of the LLM: `classifyQuestionSensitivity` is pure and synchronous, runs even with `OPENROUTER_API_KEY` unset (`askQuestionAction`'s `rulesetSensitive` re-check), and a spy on `generateGrounded`/`classifySensitiveLlm` can assert the writing model was never invoked for a sensitive question — the block does not depend on trusting the model to refuse itself.
- **Trade-off, accepted:** the keyword ruleset over-blocks by design — "pay" and "comp" alone as single-word matches will catch some phrasing that isn't actually asking about compensation eligibility. That's the intended failure direction: a false positive costs the user one manual answer; a false negative would risk an autonomous answer to a protected-class question, which this project's risk posture treats as unacceptable at any rate.
- **Trade-off, accepted:** `MAX_GENERATION_FACTS` (12) and the relevance scorer's shared-word heuristic mean a well-populated fact bank can still lose a relevant fact to the cap — acceptable because `NEEDS_FACTS` and the provenance chips make the selected subset visible and correctable (add a more specific fact, or answer manually) rather than silently degrading answer quality.
- **Risk to watch:** the sensitive-term list is static and English-only; a question phrased in another language or an unlisted synonym would fall through to the LLM tie-break (which can still widen it) but has no ruleset-level guarantee. Any addition to spec §7.2.5's categories should extend `SENSITIVE_TERMS`, not rely on the LLM tie-break to catch the gap.
- **Follow-on:** the same `withReplay`/`AiMode` machinery this ADR establishes for `generate` and `classifySensitiveLlm` is available unchanged to any future writing-tier task (`classifyReply`, `interpretField` in P4+) — recorded once per prompt shape, replayed everywhere that needs determinism.
